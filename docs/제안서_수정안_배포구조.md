# 제안서 수정안 — 배포 구조 변경 (2026-10-28 결정)

## 결정
정적 웹앱(GitHub Pages) + 서버리스 프록시 구조 대신 **로컬 Python 서버 + SQLite** 구조를 유지한다. 접속 범위는 단계적으로 넓힌다.

| 단계 | 접속 범위 | 전제 조건 |
|---|---|---|
| 1. 개발·단독 시연 (현재) | 실행 PC 1대(127.0.0.1) | 없음 |
| 2. 수업 내 다인 사용 | 학교 내부망 | 로그인·역할 구분(피해자/담당자/봉사자), CSRF 방어 구현 후 |
| 3. 외부 접속 | HTTPS 클라우드 서버에 같은 Python 서버 배포 | 2단계 조건 + TLS, 운영 보안 점검 |

**이유**
1. 세 역할이 같은 신고·승인 상태를 공유해야 핵심 흐름(요청 → 승인 → 행동)이 성립한다. 브라우저 안에만 상태를 두면 다른 기기의 담당자가 요청을 볼 수 없다.
2. 승인 대기열, 감사 기록, 동시 승인 방지, 검증 통과분만 표시하는 규칙을 서버가 강제한다. 브라우저 쪽 승인은 화면 조작으로 우회될 수 있다.
3. 서버가 API 키를 환경변수로 보관하므로 별도 프록시가 필요 없다.
4. Web Serial API는 localhost에서도 동작하므로 마이크로비트 게이트웨이 연결에 지장이 없다.

**대가**: G5(설치 없이 브라우저로 접속)는 3단계 전까지 충족하지 못한다. 입력 원문은 마스킹 후 서버 DB에 저장한다.

## 고칠 문안 (제안서 절별)

### 1. 요약 — 표의 '배포' 행
- 기존: GitHub(웹앱) + 키 보호용 프록시, 상태는 브라우저 안에서 관리
- 수정: 로컬 Python 웹 서버 + SQLite(키는 서버 환경변수에 보관). 다인 접속은 로그인·권한 구현 후 학교 내부망 또는 HTTPS 서버로 확장

### 4.1 목표 — G5
- 기존: 설치 없이 브라우저로 접속해 쓸 수 있다 / 확인 방법: 배포 주소 접속
- 수정: 실행 PC에서 브라우저로 모든 역할 화면을 쓸 수 있고, 같은 서버를 내부망·HTTPS 서버에 올리면 설치 없이 접속할 수 있다 / 확인 방법: 1단계 로컬 접속, 3단계에서 배포 주소 접속(이번 범위에서는 선택)

### 9. 시스템 아키텍처 — 도입 문단
- 수정: 웹앱 화면은 브라우저에서, 에이전트 실행·승인 대기열·감사 기록은 Python 서버에서 처리하고 데이터는 SQLite에 저장한다. 업스테이지 API 키는 서버 환경변수에만 두며 브라우저로 보내지 않는다. 현장 장치는 USB 직렬로 브라우저(localhost)에 연결되고, 브라우저가 이벤트를 서버 API로 전달한다.

### 9.1 구성 요소 — 표
| 구성 | 역할 | 기술 선택 | 비고 |
|---|---|---|---|
| 웹 화면 | 역할 화면, 상황판, 센서 시뮬레이터 | HTML/JavaScript(서버가 제공) | 접수 사이트 `/report`, 관리자 `/admin` |
| 웹 서버 | 에이전트 실행, 승인 대기열, 감사 기록, API 키 보관 | Python 표준 라이브러리 HTTP 서버 | 기본 127.0.0.1 바인딩 |
| 데이터베이스 | 신고, 승인, 감사 로그 | SQLite(마이그레이션 버전 관리) | 원문은 마스킹 후 300자까지 저장 |
| 직렬 연결 | 게이트웨이와 브라우저 사이 데이터 | Web Serial API | Chrome·Edge 데스크톱, localhost 또는 HTTPS |
| 업스테이지 API | 문장 해석·초안, 근거 검증 | OpenAI 호환 채팅 엔드포인트 | 서버에서만 호출 |
| 설정·규칙 데이터 | 구역, 안내 조각, 지원제도 규칙 | 저장소의 JSON | 출처·기준일 필드 |
- '프록시' 행은 삭제한다.

### 9.2 데이터 흐름
- 2번: 사용자 입력 → 서버 API → 입력 정제·마스킹 → ② 접수(서버에서 Solar 호출) → SQLite 저장·접수함
- 4번: ③ 초안 → ⑦ 검증 → 통과분만 승인 대기열(SQLite) → 담당자 승인 → 접수 사이트에 근거와 함께 표시

### 9.3 AI 호출 구조
- 기존: 브라우저 → 프록시 → 업스테이지
- 수정: 브라우저 → 서버 → 업스테이지. 서버가 키를 붙이고 세션 호출 한도·캐시·입력 길이 제한을 적용한다.

### 9.4 배포와 보안
- 수정:
  - 1단계는 실행 PC에서만 접속한다(127.0.0.1 바인딩, 다른 주소는 서버가 거부).
  - API 키는 서버 환경변수에만 두고 저장소·HTML·채팅에 넣지 않는다. 노출이 의심되면 즉시 교체한다.
  - 다른 기기에 열기 전에 로그인·역할별 권한·CSRF 방어를 먼저 구현한다.
  - 외부 접속이 필요하면 HTTPS 서버에 배포하고 운영 보안 점검을 거친다.

### 10.3 1차시 — 기반·배포
- 작업: 'GitHub Pages 배포 경로, 프록시' → '로컬 서버 실행 경로, 서버 환경변수 키 관리, SQLite 마이그레이션'
- 종료 기준: '외부 네트워크에서 배포 주소에 접속되고, 프록시를 거친 두 API 호출이 성공' → '실행 PC에서 서버에 접속되고, 서버를 거친 두 API 호출(Solar, Groundedness)이 성공하며, 저장소에 키가 없음을 확인'

### 10.5 결정 사항
- 3번 '프록시 서비스 선택' → '다인 접속 단계(내부망/HTTPS 서버)와 시점'

### 12.1 위험 관리표
- R2 대응: '프록시의 비밀 변수' → '서버 환경변수'
- 추가 — R16 인증 없는 관리자 화면 노출 / 영향: 무단 승인 / 대응: 127.0.0.1 바인딩, 다인 접속 전 로그인·권한·CSRF 구현

### 12.2 개인정보와 윤리 원칙 — 3번
- 기존: 원문 비저장 — 입력한 문장은 서버에 저장하지 않고 브라우저 안에서만 처리
- 수정: 최소 저장 — 입력한 문장은 개인정보 형태를 마스킹하고 300자까지만 로컬 DB에 저장한다. 가상 데이터만 쓰며, 시연 후 DB를 초기화할 수 있게 한다.
